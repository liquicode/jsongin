Correctness

15 findings · verified

Ordered roughly by how quietly each one fails. The first three return wrong answers with no error, no log, and no exception.

C1Data loss

Unhybridize() silently drops any string that parses as JSON

src/jsongin/Unhybridize.js:20–52

JSON.parse() succeeds on the field, value.type is undefined, no case matches, and the break on line 48 leaves the block without ever assigning complicated[ key ]. The field is deleted. 

Unhybridize( { a: '123' } )    => {}
Unhybridize( { a: 'true' } )   => {}
Unhybridize( { a: '[1,2]' } )  => {}
Unhybridize( { a: 'hello' } )  => { a: 'hello' }  // survives only because JSON.parse throws
C2Data loss

Unhybridize() reads the envelope fields off the raw string

src/jsongin/Unhybridize.js:36, 39, 42

The 'd', 'o', 'a', and 'r' cases read from the parsed value. The 'e', 'f', and 'y' cases read from Document[ key ], which is still the JSON string. 

new Error( Document[ key ].message )     // undefined — should be value.message
new Function( Document[ key ].source )   // undefined — should be value.source
Symbol( Document[ key ].source )         // undefined — should be value.source

Unhybridize( Hybridize( { a: new Error( 'boom' ) } ) ).a.message   => ''
C6Data loss

Distinct() concatenates group keys with no separator

src/jsongin/Distinct.js:20–21

document_key += JSON.stringify( value ) lets two genuinely distinct documents collide onto one key, and one result is dropped. 

Distinct( [ { a: 1, b: 23 }, { a: 12, b: 3 } ], { a: 1, b: 1 } )
=> [ { a: 12, b: 3 } ]   // both key to "123"

Operators/Stage/group.js:35 already solves this correctly, prefixing the short type and building one key per value. Line 20 additionally writes the source value into the result by reference, so mutating the result mutates the input documents.

C3Invalid output

Format() emits invalid JSON for quotes, backslashes, and control characters

src/jsongin/Format.js:73

String.replace() with a string pattern replaces only the first occurrence, and nothing escapes \, \n, or \t at all. All three cases below fail JSON.parse. 

Format( { a: 'x"y"z' } )       => {"a":"x\"y"z"}
Format( { a: 'a\nb' } )        => {"a":"a<LF>b"}     // bad control character
Format( { a: 'back\\slash' } ) => {"a":"back\slash"}  // bad escaped character
C4Invalid output

Parse() discards string escape sequences

src/jsongin/Parse.js:65–76

The tokenizer consumes the backslash and takes the next character literally, so escapes decode to their own letters. Parse is documented as “similar to JSON.parse()”, so valid JSON it decodes wrongly is a defect rather than a documented limitation. 

Parse( '{"a":"x\ny"}' )      => { a: 'xny' }       JSON.parse: { a: 'x\ny' }
Parse( '{"a":"xAy"}' )  => { a: 'xu0041y' }   JSON.parse: { a: 'xAy' }

Taken with C3, the two functions round-trip with neither JSON nor each other.

C5Error handling

Parse() crashes with a raw TypeError on truncated input

src/jsongin/Parse.js:126, 138

The while ( Tokens[ 0 ].token !== ']' ) loops never test for an exhausted token array. Every other entry point in the library reports a described error; this one reports a Javascript internal. 

Parse( '[' )  => TypeError: Cannot read properties of undefined (reading 'token')
Parse( '' )   => undefined
C8Aliasing

Project() computed fields alias the source document

src/jsongin/Project.js:119

Included fields are cloned on the way out (line 104). Computed fields are not, and Evaluate() returns live references for field references. 

let doc = { user: { name: 'Alice' } };
let p = jsongin.Project( doc, { copy: '$user' } );
p.copy.name = 'MUTATED';
doc.user.name   => 'MUTATED'

Operators/Stage/group.js:122 clones on output with a comment stating the rule — “derived data must never alias what it came from”. Project is the outlier.

C9Aliasing

$set and $push alias the update document

src/Operators/Update/Field/set.js · src/Operators/Update/Array/push.js:32

Update() clones the document (Update.js:14), but the values come from the update spec by reference. $addToSet clones correctly, so sibling operators disagree with each other. 

let spec = { $set: { obj: { n: 1 } } };
let out = jsongin.Update( {}, spec );
out.obj.n = 999;
spec.$set.obj.n   => 999
C10Injection

Text.SearchReplace builds a RegExp from unescaped keys

src/Text.js:74, 81

new RegExp( Object.keys( ReplacementMap ).join( '|' ), 'g' ) interprets regex metacharacters in the search text. A wildcard match then fails the ReplacementMap[ matched ] lookup and interpolates the literal string "undefined" into the output. 

SearchReplace( 'a.b axb', 'a.b', 'X' )  => 'X undefined'  expected 'X axb'
SearchReplace( 'c(d)', '(', '[' )       => SyntaxError: Invalid regular expression
SearchReplace( 'a+b', '+', '-' )        => SyntaxError: Invalid regular expression

Text.Matches on line 59 already escapes its pattern. These two do not.

C12MongoDB parity

$currentDate never stores a Date, and fails silently on a malformed spec

src/Operators/Update/Field/currentDate.js:32, 42, 46
Update( {}, { $currentDate: { f: true } } ).f
  => '2026-08-14T07:30:39.309Z'  // a string, not a Date
Update( {}, { $currentDate: { f: { $type: 'date' } } } ).f
  => 'Fri Aug 14 2026'            // time-of-day lost

Query( that_document, { f: { $type: 'date' } } )  => false

The value fails a $type: 'date' query against its own output. Update.js:13 deliberately uses SafeClone “so that dates survive an update”, which reads as an intent that dates be real Dates.

Separately, an object spec with no $type string falls through lines 35–55 with value still null: no field written, no OpLog, and true returned. Operator-Reference.md:447 discloses the string behaviour; it does not disclose the silent success.

C7MongoDB parity

BsonType() reports int for every safe integer

src/jsongin/BsonType.js:39–46

Number.isSafeInteger() is not an int32 range test, but the branch it guards returns 16 and the comment says int32. The $type operator is built directly on this, so the deviation is user-visible. 

BsonType( 3000000000, true )                           => 'int'   MongoDB: 'long'
Query( { a: 3000000000 }, { a: { $type: 'int'  } } )   => true   should be false
Query( { a: 3000000000 }, { a: { $type: 'long' } } )   => false  should be true
C11MongoDB parity

$eq and $ne do not handle a RegExp match value

src/Operators/Query/Comparison/eq.js:29

'r' sits in the primitive branch, so two RegExp objects are compared with === and never match. The implicit form routes to $regex (ImplicitEq.js:132); the explicit form does not. 

Query( { a: 'hello' }, { a: /ell/ } )           => true
Query( { a: 'hello' }, { a: { $eq: /ell/ } } )  => false  MongoDB: true
Query( { a: 'hello' }, { a: { $ne: /ell/ } } )  => true   MongoDB: false
C13Path handling

SplitPath converts any numeric-looking element to a number

src/jsongin/SplitPath.js:30

AsNumber() accepts '1e2', '01', '0x10', and 'Infinity', so field names in those forms become array indices. Only canonical integer text — plus the documented negative-index extension — should. 

GetValue( { '01': 'x' }, '01' )    => undefined
GetValue( { '1e2': 'x' }, '1e2' )  => undefined
SetValue( {}, 'a.01', 'x' )        => { a: [ null, 'x' ] }  expected { a: { '01': 'x' } }
C14Round trip

Flatten / Expand lose empty objects and arrays

src/jsongin/Flatten.js:13–32

An empty container has no leaf to emit, so it disappears rather than round-tripping.

Flatten( { a: {}, b: [] } )            => {}
Expand( Flatten( { a: {}, b: [] } ) )  => {}
C15Latent

Stray circular require at the top of three modules

src/jsongin/GetValue.js:3 · Parse.js:3 · Format.js:3
const jsongin = require( '../jsongin' );

src/jsongin.js assigns module.exports only after building the engine, so this resolves to the partially-initialized {}. It is inert today because the factory parameter of the same name shadows it inside every function — but it is a load-order landmine, and it reads as intentional.

Consistency

Mostly places where the code and its own documentation have drifted apart. S1 is the one worth deciding before more operators are written against the claim.

S1Unenforced contract

ValueTypes, ArgTypes, and ArgCount are declared everywhere and read nowhere

docs/guides/Operator-Authoring.md:91 · all 76 operator modules

The authoring guide states that ValueTypes is “the ShortTypes this operator accepts as its MatchValue. A query which gives it anything else is rejected.” A scan of src/, test/, and build/ finds exactly one read of any operator metadata member: TopLevel, at src/jsongin/Query.js:46. 

$size ValueTypes = 'n'
Query( { a: [ 1, 2 ] }, { a: { $size: 'two' } } )  => false, not rejected

Either enforce it in Query() and Evaluate(), or stop documenting it as enforcement.

S4Doc is wrong

StrictEquals is documented as ===

docs/guides/Library-Guide.md:137

It is CompareValues( A, B ) === 0, which is a different relation:

StrictEquals( null, undefined )               => true
StrictEquals( new Date( 0 ), new Date( 0 ) )  => true
StrictEquals( { a: 1 }, { a: 1 } )            => true

The comment at src/jsongin.js:213–219 explains the real rule well. The guide should say what that comment says.

S5Doc is wrong

Usage-Browser.md claims the two browser globals are the same instance

docs/guides/Usage-Browser.md:31–44 · src/jsongin.js:3, 332

window.jsongin is webpack's UMD export, which is the instance built at src/jsongin.js:3. window.liquicode.jsongin is a second engine from the NewJsongin() call on line 332. Verified distinct: an operator registered on one is not visible on the other. Since Operator-Authoring.md:201 specifically warns that registries are per-instance, this matters.

Note also that src/jsongin.js:333 has // window.jsongin = jsongin; commented out — the global the doc describes comes from webpack, not from that line.

S6Overclaim

The readme makes a blanket MongoDB-accuracy claim the reference contradicts

readme.md:59 · docs/guides/Operator-Reference.md:447, 451

The readme says “Each MongoDB feature that is implemented here, operates accurately and in accordance with MongoDB.” The Operator Reference correctly discloses that $currentDate stores strings and that $push is partially implemented. The reference is the honest document; the readme should be softened to match it.

What is solid

The larger part of the picture
Docs

The docs and code do not drift on surface area. Every public engine member has a page under docs/guides/jsongin/, and every page has a member. Verified in both directions, zero mismatches. That is rare.

Tooling

The build tooling is real, not decorative. docs-check.js validates 285 code fences by parsing them, 249 local links, and orphaned pages, and it is wired into build_docs as a halting step. coverage.js classifies uncovered blocks by kind rather than just counting lines.

Architecture

The operator layer is genuinely consistent. 76 modules, one per file, uniform factory shape, per-instance registries, uniform OpLog/OpError plumbing. Adding an operator is obvious, which is the whole point of the design.

Immutability

Aggregate gets immutability right. Aggregate.js:19 slices, $group and $unwind clone on output, and both say so in their /*md blocks. The caller's array and documents are verified untouched.

Snapshots

Diff and Invert round-trip correctly across nested objects, arrays, dates, additions, and removals. Invert computing the inverse from the observed result rather than from the patch operators is a good design call, and the comment explains why.

Edge cases

The hard comparison cases are handled deliberately. CompareValues handles the NaN ordering trap explicitly, with a comment on why falling through would make sorts arbitrary. Sort correctly separates MongoDB's array sort-key rule from element-wise array comparison — a subtlety most implementations miss.

Comments

The tricky semantics are commented where they are decided, not only in the guides: StrictEquals vs $eq asymmetry, Merge vs RFC 7386 null handling, SafeClone vs Clone for dates.

  2. C3, C4, C5 — Parse and Format round-trip with neither JSON nor each other.
  3. C8, C9, C10, C12 — the aliasing pair, the Text regex escaping, and $currentDate.

  5. S1 — decide whether ValueTypes is enforcement or documentation, then make the code and the guide agree. S2 and S3 fall out of that decision.
  6. S4, S5, S6 — three published statements that are currently false.
  7. C7, C11, C13, C14, S7, S8 and the remaining consistency items.
